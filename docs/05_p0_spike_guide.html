S1

Does Synthea emit vitals at ward cadence?

blocks the core claim

The question: can you form a 12-timestep window of six vitals whose readings sit hours apart rather than months apart? If not, your windows are life-history, and the "real-time telemetry" gap you claim against b5 cannot be claimed on this dataset.

  1. Generate a small cohort

    Fifty patients is plenty — you are measuring a distribution, not training anything.

    git clone https://github.com/synthetichealth/synthea.git
cd synthea
.\run_synthea.bat -p 50 --exporter.csv.export true --exporter.fhir.export false

    Output lands in synthea/output/csv/. You need observations.csv.

  2. Check whether timestamps even carry a time of day

    This is the fastest possible disqualifier. If Synthea writes date-only values, or writes every observation at the same clock time, sub-day cadence is not representable at all and the rest of the spike is moot.

    import pandas as pd

df = pd.read_csv("synthea/output/csv/observations.csv", low_memory=False)
print(df["DATE"].astype(str).head(10).tolist())

df["DATE"] = pd.to_datetime(df["DATE"], errors="coerce", utc=True)
print("rows:", len(df))
print("distinct times-of-day:", df["DATE"].dt.time.nunique())

    A distinct-times count in the single digits means observations are pinned to synthetic clock slots, not sampled through a day.

  3. Find out what Synthea actually emits — don't assume your LOINC list

    Your guide fixes seven codes up front. Verify they are present and frequent before building a pipeline around them; Synthea's code choice varies by module and version.

    top = (df.groupby(["CODE", "DESCRIPTION"]).size()
         .sort_values(ascending=False).head(25))
print(top.to_string())

VITALS = ["8867-4", "8480-6", "8462-4", "59408-5", "9279-1", "8310-5", "2339-0"]
present = df[df["CODE"].isin(VITALS)]["CODE"].value_counts()
print("\nyour seven codes, as found:")
print(present.reindex(VITALS).fillna(0).astype(int).to_string())
    Expect a surprise hereAny code returning 0 needs substituting before P2. SpO2 and glucose are the two most likely to differ from the codes in your guide.

  4. Measure the gap distribution

    v = df[df["CODE"].isin(VITALS)].sort_values(["PATIENT", "CODE", "DATE"]).copy()
v["gap_h"] = (v.groupby(["PATIENT", "CODE"])["DATE"]
                .diff().dt.total_seconds() / 3600)

print(v.groupby("CODE")["gap_h"]
       .describe(percentiles=[.25, .5, .75])
       .round(1).to_string())

    Read the median column. Hours means telemetry. Thousands of hours means annual checkups.

  5. The decisive test — can a 12-step window be formed at all?

    A median gap is suggestive; this is the actual requirement. Count patients who have a run of 13 consecutive readings where every gap is within a tolerance.

    def longest_run(times, max_gap_h):
    """Longest run of readings each within max_gap_h of the previous one."""
    t = times.sort_values()
    if len(t) < 2:
        return len(t)
    within = t.diff().dt.total_seconds().div(3600).le(max_gap_h)
    best = run = 1
    for flag in within.iloc[1:]:
        run = run + 1 if flag else 1
        best = max(best, run)
    return best

hr = v[v["CODE"] == "8867-4"]
for tol in [1, 6, 24, 24 * 7, 24 * 30]:
    runs = hr.groupby("PATIENT")["DATE"].apply(longest_run, max_gap_h=tol)
    n_ok = int((runs >= 13).sum())
    print(f"max gap {tol:>6}h -> {n_ok:>3}/{runs.size} patients can form a 12-step window")

PASS

FAIL
Few or no patients form windows below a multi-week tolerance. Synthea has clinical structure but no telemetry. Choose one of the three paths below and write down which.

S2

Do Opacus, Flower, and a sequence model actually compose?

highest engineering risk

The question: can one ward node train a recurrent model under DP-SGD inside a federated round and report a privacy budget that means what the paper will claim it means? Build this in the order below — each layer is only debuggable once the one beneath it is known good.

  1. Confirm the model is even DP-compatible

    Opacus computes per-sample gradients and cannot do so for every layer type. Run the validator before anything else.

    import torch.nn as nn
from opacus.validators import ModuleValidator

plain = nn.LSTM(6, 64, num_layers=2, batch_first=True)
print(ModuleValidator.validate(plain, strict=False))
    Trap 1 · this breaks the model code in your guide nn.LSTM and nn.GRU are not supported. Opacus ships DPLSTM and DPGRU in opacus.layers as drop-in replacements, and ModuleValidator.fix() will not substitute them for you. The LSTM and GRU classes in your Research Guide will fail at make_private as written.

  2. Smoke test A — DP training on one node, no federation

    import torch, torch.nn as nn
from torch.utils.data import TensorDataset, DataLoader
from opacus import PrivacyEngine
from opacus.layers import DPLSTM

class Net(nn.Module):
    def __init__(self, inp=6, hid=64, layers=2):
        super().__init__()
        self.rnn = DPLSTM(inp, hid, layers, batch_first=True)
        self.fc  = nn.Linear(hid, 1)
    def forward(self, x):
        out, _ = self.rnn(x)
        return self.fc(out[:, -1, :])        # logits, NOT sigmoid

X = torch.randn(2048, 12, 6)
y = (torch.rand(2048) > 0.85).float()
dl = DataLoader(TensorDataset(X, y), batch_size=32, shuffle=True)

model = Net()
opt   = torch.optim.SGD(model.parameters(), lr=0.01, momentum=0.9)
crit  = nn.BCEWithLogitsLoss()

pe = PrivacyEngine()
model, opt, dl = pe.make_private_with_epsilon(
    module=model, optimizer=opt, data_loader=dl,
    target_epsilon=2.0, target_delta=1e-5,
    epochs=5, max_grad_norm=1.0,
)

for _ in range(5):
    for xb, yb in dl:
        opt.zero_grad()
        crit(model(xb).squeeze(-1), yb).backward()
        opt.step()

print("achieved epsilon:", pe.get_epsilon(delta=1e-5))
    Trap 2 · a real bug in your model spec Your Research Guide's models end with torch.sigmoid(self.fc(...)), while the data plan specifies BCEWithLogitsLoss with pos_weight for class imbalance. That loss applies sigmoid internally — feeding it already-sigmoided output squashes predictions into roughly [0.5, 0.73] and gradients nearly vanish. Return raw logits, as above, or switch to plain BCELoss and lose the pos_weight handling. Fix this in the spec now, not after a training run looks mysteriously flat.

  3. Smoke test B — federation with no DP

    Two clients, two rounds, FedAvg, plain nn.LSTM. Confirm the loop runs and loss moves. Use your pinned Flower version's own simulation API — this is where version churn bites, so follow the docs for the exact version you pinned rather than a blog post.

    You are checking one thing only: that parameters make the round trip and aggregation happens. Do not add DP yet.

  4. Smoke test C — compose them, and check the accountant across rounds

    Now combine: DPLSTM, per-client PrivacyEngine, two federated rounds. Then run the test that matters.

    # Run 2 rounds. Print epsilon after round 1 and after round 2.
# If the two numbers are IDENTICAL, your accountant is resetting
# every round and your "epsilon over 100 rounds" claim is false.
    Trap 3 · the accounting claim most likely to be wrong A fresh PrivacyEngine per round starts a fresh accountant, so the ε you print is per-round, not cumulative. C4 claims a tight bound across 100 rounds — that requires accounting over all of them. The defensible fix is to size the noise once for the total step count and hold it fixed: 
    from opacus.accountants.utils import get_noise_multiplier

TOTAL_STEPS = ROUNDS * LOCAL_EPOCHS * steps_per_epoch
sigma = get_noise_multiplier(
    target_epsilon=2.0, target_delta=1e-5,
    sample_rate=batch_size / len(local_dataset),
    steps=TOTAL_STEPS, accountant="rdp",
)
# then make_private(noise_multiplier=sigma, max_grad_norm=1.0) each round
    Note also that the import path in your Research Guide (opacus.accountant.analysis.rdp) does not exist — the module is opacus.accountants, plural, and get_noise_multiplier lives in its utils.

  5. Decide and record what your ε actually protects

    Opacus gives sample-level DP within each client. Your samples are sliding windows, and one patient contributes many overlapping windows — so a per-window ε of 2 does not mean each patient enjoys ε = 2. Under group privacy, a patient contributing k windows carries a substantially looser bound.

    Reviewers in health privacy will ask this Decide now and state it explicitly in the paper: either report the unit of privacy as the window and give the implied patient-level bound alongside it, or restructure sampling so the privacy unit is the patient. Do not let the paper imply patient-level protection from a window-level accountant.
Decision rule
PASS
Smoke test C runs, ε accumulates across rounds, and per-round wall-clock is recorded. Feed that timing straight into S4.
FAIL
Time-box expired. Fall back to the 1D CNN alone, which Opacus supports natively — but understand this guts C2, since the whole contribution is recurrent versus convolutional. Escalate to the mentor before accepting that trade.
S3

How does PTB-XL become model input?

design decision, not a build

The question: PTB-XL is 10-second 12-lead waveforms; your models take a [batch, 12, 6] tensor of tabular vitals. No mapping between them exists in any of your documents. Since PTB-XL is the single highest-leverage item in your whole plan, the mapping needs deciding before P2 builds a pipeline for it.

  1. Get the 100 Hz version only

    The 500 Hz records are roughly ten times the size and buy you nothing at this stage. Open access, no credentialing.

  2. Inspect one record and confirm the shape

    Load a single record with wfdb. You should see roughly 1000 samples × 12 leads for a 10-second strip at 100 Hz. Confirm this before planning anything around it.

  3. Settle the labels

    Use scp_statements.csv to map SCP codes to diagnostic superclasses, then collapse to binary: NORM versus everything else. Record the resulting class balance — it will differ markedly from your Synthea anomaly rate, and that difference has to be handled or acknowledged when comparing curves.

  4. Choose the mapping — recommended path first

    Option A, recommended. Extract per-interval physiological features and build windows from those: heart rate, RR-interval variability, QRS duration, ST level, T-wave amplitude, per-lead voltage statistics. Segment the 10-second strip into intervals and compute features per interval, giving windows of timesteps × features that your existing architecture consumes unchanged. neurokit2 handles the R-peak detection and delineation.

    Option B, acceptable. Accept a different input width for PTB-XL and claim only that the shape of the ε-utility curve transfers, not absolute F1. Cheaper, and honest.

    Not defensible. Naively downsampling twelve raw leads into a 12 × 12 grid to force shape compatibility. It is arithmetically neat and physiologically meaningless, and a reviewer who knows ECG will say so.

  5. Write down what the PTB-XL result will and will not claim

    Phrase this carefully in the paper PTB-XL is diagnostic ECG classification, not deterioration detection from ward vitals. The defensible claim is that the ε-utility trend observed on synthetic vitals also appears on real physiological signals — evidence that your finding is not a synthetic-data artifact. It is not evidence that your anomaly detector works on real patients. Overclaiming here converts your strongest defensive asset into an attack surface.
Decision rule
DONE
The mapping is written down, one sample tensor of the right shape exists, and the claim wording is drafted.
S4

Does the experimental grid fit the compute you have?

sizes every later phase

The question: how long does one full run actually take on your hardware, and does the grid you have specified fit in the calendar time available? Cut the grid here, deliberately — not in Phase 4, in a panic.

  1. Time one run at the real configuration

    Not a reduced smoke-test config — the real one: full rounds, all clients, real local epochs, DPLSTM. Time a few rounds and extrapolate linearly.

    Expect this to hurt DPLSTM is materially slower than nn.LSTM, which uses fused cuDNN kernels that per-sample gradient computation cannot use. Per-sample gradients also multiply memory. Measure it; do not estimate it from experience with ordinary training.

  2. Do the arithmetic

    GridCompositionRuns
    Core, clean Synthea3 models × 6 ε levels × 5 seeds90
    Noise-injected Syntheabest model × 6 ε × 5 seeds30
    PTB-XLbest model × 6 ε × 5 seeds30
    Totalbefore any dropout or heterogeneity runs150

    Multiply by your measured per-run time. At 20 minutes a run that is 50 hours; at 90 minutes it is 225 hours, which is over nine days of uninterrupted compute — on a machine Person A also needs for Ollama.

  3. Measure GPU contention

    Run a DP training round while Ollama serves a query. If they collide badly, decide now whether the product demo and the campaign get separate machines, separate time windows, or CPU-only inference.

  4. Fix the grid, and fix the seed count with the statistics in mind

    The seed count is not only a compute decision — it determines what C2 can conclude. As flagged in the execution plan, five seeds per group with twelve Bonferroni-corrected pairwise tests cannot reach significance under any outcome, because the smallest attainable p at that sample size sits above the corrected threshold.

    Resolve both together Either adopt a single omnibus model over architecture × ε — more powerful, fewer tests, and a better match to the actual question — or raise the seed count and reduce the number of comparisons. Decide this now, because it changes the number of runs S4 has to budget for.
Decision rule
PASS
Measured per-run time × final grid fits the available wall-clock with margin for reruns. Record the final grid.
FAIL
Descend the de-scoping ladder from the execution plan until it fits — drop GRU first, then the noise-injected variant. Never trade away PTB-XL or the seed count to save compute.

The actual deliverable

P0 exit gate

Write one short memo answering all of the below, and have both team members and the mentor read it. P0 is not complete because the spikes ran — it is complete because the decisions are recorded and nothing is left as "we'll figure it out later."

The memo must state

  • S1 — the measured gap distribution, whether a 12-step window is formable and at what tolerance, and which of paths A / B / C you are taking if it is not.
  • S1b — whether the MIMIC credentialing application has been submitted. Recommended: submit it regardless.
  • S2 — pinned versions of PyTorch, Opacus, and Flower; confirmation that DPLSTM trains under a federated round; whether ε accumulates across rounds and how you are sizing noise; and the stated unit of privacy — window or patient.
  • S2b — the logits-versus-sigmoid fix applied to the model spec.
  • S3 — the chosen PTB-XL mapping, the resulting input shape, the label balance, and the drafted wording of what that experiment claims.
  • S4 — measured per-run wall-clock, the final grid, the total compute estimate, and the GPU-sharing plan.
  • S4b — the revised statistical plan for C2, with the seed count that plan requires.

Then, and only then, P1 begins. Every one of these answers is an input to the scope lock — starting P1 without them means locking a scope built on assumptions you chose not to test.
