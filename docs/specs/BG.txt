


## 1. Local LLM (Large Language Model)

**What it is:** An LLM is a neural network trained on huge amounts of text that can understand and generate human-like language — this is the "brain" behind ChatGPT, Claude, etc.

**"Local" means:** Instead of sending your questions to a company's cloud server (like how ChatGPT runs on OpenAI's servers), the model runs entirely on hardware you control — a hospital's own server or device.

**Why it matters here:** Patient health data is extremely sensitive. If you sent it to a cloud LLM API, that data would leave the hospital's control and go to a third party — a legal and ethical problem (HIPAA-type regulations, patient trust). Running the LLM locally means the model comes to the data, not the other way around.

**How you'd actually run one:** Tools like **Ollama** or **llama.cpp** let you download an open-weight model (like Llama 3.1 8B or Mistral 7B — "8B"/"7B" means billions of parameters, roughly its "brain size") and run it on a regular GPU or even decent CPU. It works offline, no internet required after setup.

**Tradeoff:** Local models are usually smaller and slightly less capable than giant cloud models (GPT-4, Claude), but they're private and don't cost per-query API fees.

## 2. RAG (Retrieval-Augmented Generation)

**The problem it solves:** An LLM by itself only knows what it learned during training — it has no idea who your specific patient is, what their lab results were yesterday, or what they ate for lunch. It also can "hallucinate" (confidently make things up).

**How RAG works, step by step:**
1. You keep the patient's actual data (lab reports, vitals, logs, notes) in a database.
2. When the patient asks a question ("How's my blood sugar trending?"), the system first **retrieves** the relevant pieces of that patient's data.
3. That retrieved data gets inserted into the prompt sent to the LLM, e.g.: *"Here is the patient's glucose readings for the last 5 days: [data]. Question: How's my blood sugar trending?"*
4. The LLM then **generates** an answer grounded in that real data, instead of guessing.

**Why this matters for your project:** RAG is what makes the assistant "personalized" — the same base LLM serves every patient, but each patient's session retrieves only *their* data, keeping it grounded and specific.

## 3. Federated Learning (FL)

**The core idea:** Normally, to train a good machine learning model, you'd gather everyone's data into one place and train on it centrally. FL avoids that.

**How it works:**
1. Imagine several hospital wards, each with their own local patient data — Ward A, Ward B, Ward C.
2. A shared model (small, e.g., an anomaly detector) is sent to each ward.
3. Each ward trains that model **locally** on its own data — nobody else sees the raw patient data.
4. Instead of sending data back, each ward sends only the **model updates** (the learned adjustments — essentially just numbers describing what the model learned) to a central coordinator.
5. The coordinator averages these updates together into an improved shared model.
6. This improved model is sent back out, and the cycle repeats.

**End result:** You get a model that's learned from many wards' worth of patients, without any raw patient data ever leaving its ward.

**In your project:** Since you don't have real multi-hospital data, you'll **simulate** this — create several synthetic "ward nodes" from your MIMIC + synthetic dataset, and run the FL process across them using a framework like **Flower** or **PySyft** (Python libraries built specifically for simulating/running federated learning).

**Important nuance:** You're not federating the whole LLM (way too heavy/complex for a two-person project) — you're federating a small downstream model, like a classifier that flags "this patient's vitals look abnormal."

## 4. Differential Privacy (DP)

**The problem FL alone doesn't fully solve:** Even though raw data never leaves each ward in FL, the model *updates* sent back can still leak information. Clever attackers can sometimes reverse-engineer details about individual patients just from those updates (this is called a "reconstruction" or "membership inference" attack).

**What DP does:** It adds carefully calibrated random noise to the data or the model updates, so that:
- The model still learns useful overall patterns
- But no single patient's data can be confidently reverse-engineered from the output

**The privacy budget, epsilon (ε):** This is the key knob. It controls how much noise gets added.
- **Low ε (e.g., 0.1)** = a lot of noise = very strong privacy, but the model's accuracy suffers (predictions get noisier/worse)
- **High ε (e.g., 10)** = little noise = weaker privacy, but better model accuracy

Think of ε like blurring a photo to hide a face — blur it a lot (low ε) and it's very private but you can barely recognize anything; blur it a little (high ε) and it's more useful but less private.

**How you'd implement it:** Usually via **DP-SGD** (Differentially Private Stochastic Gradient Descent) — a modified version of the standard algorithm used to train neural networks, which clips and adds noise to the training updates.

**Your paper's actual experiment:** You'll train the anomaly detector at many different ε values, and plot: *as ε goes down (more private), how much does detection accuracy (F1, recall, etc.) drop?* That curve is your core research result — it shows people deploying such a system where the "sweet spot" is between privacy and usefulness.

## 5. Anomaly / Risk Detection Model

This is the actual small ML model being federated and made differentially private. It's not the LLM — it's a simpler, traditional model (like a classifier or a lightweight neural net) trained to look at a patient's numeric data (vitals, lab trends) and output something like: *"This looks abnormal / high-risk"* vs. *"This looks normal."*

This is what powers the **doctor-facing alert dashboard** — the doctor doesn't get bothered with every reading, only when this model flags something.

---

## 6. MIMIC-III / MIMIC-IV

These are real, de-identified (privacy-scrubbed) hospital ICU datasets released for research — containing real vitals, lab results, and clinical data from tens of thousands of actual patients, but with identifying details removed. They're free but require a short training course + credentialed access approval (hence why you should apply early). You'll use this for realistic vitals/lab data, since it's far more credible than fully made-up numbers.

**What MIMIC won't have:** conversational logs with an AI assistant, or nutrition/exercise tracking data — because those aren't things that dataset was built for. That's why you'll need to **generate synthetic data** for those parts (e.g., using an LLM to generate plausible sample conversations/logs, following clinical templates so they're realistic).

---

## 7. Encrypted Local Storage

This just means the patient's data, when saved to disk, isn't stored as plain readable text — it's scrambled using an encryption algorithm (e.g., AES) so that even if someone accessed the raw files without permission, they couldn't read them without the decryption key. Combined with local-only processing, this is your "defense in depth" — even inside the hospital network, data is protected at rest.

---

## 8. How It All Fits Together (the full picture)

Here's the request flow, end to end, for a patient interacting with the assistant:

1. **Patient logs data** (meal, symptom, exercise) → stored in encrypted local database.
2. **Patient asks a question** → RAG layer retrieves their relevant data → local LLM generates a grounded answer.
3. **In the background**, the anomaly detection model (trained via FL+DP across simulated wards) continuously scores the patient's vitals/logs.
4. **If it flags something abnormal** → an alert appears on the doctor's dashboard.
5. **Doctor queries the system** → gets a plain-language summary of the patient's recent status, pulled via the same RAG approach but from the doctor's interface.

The LLM (conversational, local, RAG-grounded) and the anomaly detector (federated, differentially private, small model) are **two separate AI components** doing two different jobs — that distinction is actually one of the more sophisticated/correct design choices in this plan, since federating a whole LLM would be unrealistic for your scope.

---

## 9. Why This Structure Makes a Good Paper

Your paper isn't "we built an app" — it's a **measurable scientific question**: *given that patient data can't leave the ward, how much privacy (via DP) can you add to a federated anomaly-detection model before its usefulness (accuracy) breaks down?* That's a clean, testable hypothesis with real numbers and graphs — which is exactly what reviewers want, versus a vaguer claim like "we made a privacy-preserving chatbot."
